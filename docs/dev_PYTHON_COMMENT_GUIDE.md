# Python 주석 작성 가이드 (dev_PYTHON_COMMENT_GUIDE)

이 문서는 `CosplayAI` 백엔드 코드의 주석 작성 규칙을 정의한다.

---

## 1. 기본 원칙

- 주석은 "무엇"보다 "왜"를 설명한다.
- 코드만으로 명확한 내용은 주석으로 반복하지 않는다.
- 공개 함수/복잡한 로직에는 docstring을 작성한다.
- 간단한 구현 디테일은 인라인 주석으로 최소한만 남긴다.

---

## 2. 모듈 주석 (파일 맨 위)

모든 서비스/파이프라인 파일은 파일 상단에 모듈 docstring을 둔다.

```python
"""
파일명: (파일 명)
작성자: (작성자 명)
설명: 모듈의 핵심 책임(1~2문장)
상위 모듈: (이 모듈을 호출하는 진입점)
하위 모듈: (이 모듈이 의존하는 주요 모듈)
"""
```

---

## 3. 함수 주석 (함수 선언 바로 아래)

현재 프로젝트 스타일을 유지하되 `Args / Returns / Raises`를 표준으로 사용한다.

```python
def build_for_basic(...):
    """
    모드 설정 파일 기준으로 최종 프롬프트를 조립한다.
    Args:
        인자명: 인자 설명은 역할/제약(필수 여부, 허용 범위)을 설명
        인자명: 자료형: 작성 규칙에 따라 자료형을 포함하여 작성
    Returns:
        반환값: 설명
        반환값: 자료형: 작성 규칙에 따라 자료형을 포함하여 작성
    Raises:
        예외 타입: 설명
    """
```

### 작성 규칙

- 반환값이 없으면 `Returns` 섹션을 생략한다.
- 예외를 던지면 `Raises`를 반드시 작성한다.
- 다음과 같은 상황에는 `Args`와 `Returns`에 자료형을 작성한다.
  - 타입힌트가 Any/너무 추상적(dict, list)일 때
  - 반환 타입이 조건에 따라 바뀔 때
  - dict/list 내부 스키마가 중요한 때 (필수 키, 원소 타입)

---

## 4. 인라인 주석

인라인 주석은 "의도"가 없으면 쓰지 않는다.

```python
# dry_run에서는 파일 저장 없이 프롬프트만 검증한다.
if dry_run:
    ...
```

### 작성 기준

- 복잡한 분기, 도메인 제약, 성능 트레이드오프가 있을 때만 작성한다.
- 한 줄 주석은 1문장으로 끝낸다.
- 코드 변경 시 주석도 같이 갱신한다.

---

## 5. 주석 태그

- `TODO`: 이후 개선할 작업.
- `FIXME`: 현재 결함 또는 위험.
- `NOTE`: 구현 의도/주의사항.
- `HACK`: 임시 우회 로직(가능하면 이슈 번호 같이 표기).

예시:

```python
# TODO: VFX 파라미터 스키마를 Pydantic으로 통합 검증
# FIXME: Windows 경로에서 백슬래시 이스케이프 이슈 가능성 있음
# NOTE: API 스펙 호환을 위해 output_filename이 없으면 timestamp를 사용
```

## 6. 요약

- 모듈: 책임과 의존 관계 중심으로 작성.
- 함수: `Args / Returns / Raises`를 기본으로 작성.
- 인라인: 의도/제약/트레이드오프가 있을 때만 작성.

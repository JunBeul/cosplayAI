# 문서 작성 가이드

이 문서는 `docs/*.md` 문서를 일관된 형식으로 작성하기 위한 기준을 정의한다.

---

## 1. 파일명 작성 규칙

현재 문서는 목적에 따라 아래 3가지로 분류한다.

| 분류      | 파일명 형식   | 예시                                |
| --------- | ------------- | ----------------------------------- |
| 개발 문서 | `dev_*.md`    | `dev_REQUIREMENTS_MANAGEMENT.md`    |
| 이슈 문서 | `issues_*.md` | `issues_img_reference_order.md`     |
| 학습 문서 | `study_*.md`  | `study_prompt_engineering_notes.md` |

작성 전, 문서의 목적을 먼저 정하고 그 목적에 맞는 접두어를 사용한다.

---

## 2. 전체 공통 규칙

- 문서 첫 문단에 "이 문서의 목적"을 1~2문장으로 명확히 쓴다.
- 큰 섹션은 `---`로 구분한다.
- 명령어/코드는 반드시 fenced code block으로 작성한다.
- 파일 경로나 엔드포인트는 백틱(`)으로 감싼다.
- 추측/감상보다 현재 동작 기준의 사실과 규칙 중심으로 작성한다.
- 문서에서 언급한 규칙/명령어가 바뀌면 관련 문서를 함께 갱신한다.
- 새 문서를 생성한 뒤에는 `README.md` 마지막 문서 섹션에 해당 문서 링크와 설명을 추가한다.

---

## 3. dev 문서 작성 규칙

`dev_*.md`는 팀의 개발/운영 기준을 남기는 문서다.

권장 구조:

1. 제목 + 목적
2. 관리 원칙(핵심 규칙)
3. 작업 절차(순서형)
4. 확인용 명령어
5. 주의 사항
6. 요약(선택)

작성 기준:

- "무엇을 해야 하는가"를 절차 중심으로 쓴다.
- 명령어는 프로젝트 실제 실행 기준으로 검증 가능한 형태로 쓴다.
- 개인 취향보다 팀 공통 기준을 우선한다.

---

## 4. issues 문서 작성 규칙

`issues_*.md`는 문제 해결 과정을 재현 가능하게 남기는 문서다.

아래 순서를 기본 템플릿으로 사용한다.

1. 제목
2. 전체 요약
3. 문제 정의
4. 원인 파악
5. 해결 방안
6. 결과
7. 관련 파일

작성 기준:

- "무슨 현상이 있었는지"와 "왜 그렇게 판단했는지"를 분리해서 쓴다.
- 해결책은 변경 포인트(코드/설정/프롬프트)를 구체적으로 남긴다.
- 가능하면 실패 로그/응답 요약 등 검증 근거를 포함한다.

---

## 5. study 문서 작성 규칙

`study_*.md`는 학습 기록 문서다. 형식은 비교적 자유롭게 작성한다.

작성 기준:

- 최종 결론만 쓰지 말고 학습 과정의 판단 근거를 함께 남긴다.
- 프로젝트에 바로 적용할 수 있는 항목은 "적용 후보"로 분리해 적는다.

---
